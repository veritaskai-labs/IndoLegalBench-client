Case review and reassignment

Before an admin replaces a reviewer, they should be able to identify the case, the person, and what happens to that person’s assessment. Aileen’s monitoring frame already makes the case and round status easy to find. The alternative brings the reviewer into that same reading path.

Nielsen evaluation

These findings come from inspection. User success rates and severity in practice still need observation. Highest priority goes to identifying the affected assignment and making the final action explicit.

HeuristicWhat worksFinding and design response
H1 · StatusText badges identify the round state independently of color.The prototype can announce success from the reassignment tab without updating the targeted slot. Show pending feedback, then name the case and replacement on confirmed success.
H2 · Familiar language“Perlu penugasan ulang” describes the admin’s task in the team’s language.The queue uses “Putaran” where admin monitoring uses “Ronde”. Use the approved frame’s “Ronde” in both.
H3 · User control“Batal” exits the form. The app retains the reviewer’s draft while history is open.Prototype “Lanjut” leaves no checkpoint. Preserve the app’s return-to-edit step and keep both fields filled.
H4 · ConsistencyThe active sidebar item, tab underline and repeated table structure give the screen a clear location.The exported headers and list have no visible sort or page controls. Use SCRUM-343 DataTable and Pager for long lists with meaningful sort keys and the accepted default order.
H5 · Prevent mistakesBoth a replacement and a reason are required in the prototype.The prototype commits through a forward-navigation label. Put the consequence and old/new names together before the final action. Retain current eligibility and duplicate-submit protection.
H6 · RecognitionCase codes and titles are available in each exported row.Identical action labels omit the affected person. Name the reviewer in the existing action column and show the actual reason beside it. If a name is unavailable, use the existing neutral fallback.
H7 · EfficiencyTabs separate work requiring action from ongoing reviews.Retain the 53 px desktop row and keep the named action in a consistent column. Reflow narrow screens and allow extra height for real content. Test the long PHK title and two affected reviewers.
H8 · Visual hierarchyThe serif heading, muted metadata, status text and monospaced IDs have distinct roles.Five solid black row buttons give every routine entry equal emphasis. Use an existing neutral row button and reserve the strongest action for the decision dialog.
H9 · Error recoveryThe app offers retry when the queue fails and distinguishes a stale assignment from a failed request.The prototype shows only populated tables. Draw separate loading, empty, fetch-failed and stale-assignment states. Keep the next action within the affected panel.
H10 · Help in contextThe replacement form explains that its reason goes into the audit log.Keep that hint. Add the consequence beside the final decision and persist the revision-comment requirement beside the reviewer’s field.

Benchmark decisions

  • Artificial Analysis groups related leaderboard columns and offers details from the entity being compared. Apply that grouping to case identity, round, and affected reviewer. Artificial Analysis leaderboard
  • GitHub separates reviewing evidence from submitting a review and lets reviewers comment on specific changes. Keep case evidence, reviewer feedback, and the explicit verdict in that order. GitHub review workflow
  • Cursor presents changes in context for inspection. Use the same principle in reassignment by showing the old and new reviewer together with the case before committing. Cursor’s review workflow

Figma handoff and usability check

Figma annotation · Reviewer button

Pada tabel desktop, atur kolom Judul ke Fill container dan kolom lain ke Hug contents. Batasi lebar tombol Ganti reviewer hingga 192 px, dengan padding sel 12 px di setiap sisi. Judul kasus yang panjang mendapat ruang tersisa.

H6, H7 · Pertahankan satu baris agar daftar mudah dipindai. Jika label “Ganti [nama]” melebihi lebar tombol, tampilkan elipsis di ujung dan perlihatkan label lengkap saat kursor diarahkan ke tombol. Adobe Spectrum — Action button, Text overflow.

Untuk Veritask, tampilkan label lengkap juga saat tombol mendapat fokus keyboard. Ketukan pada layar sentuh membuka dialog dengan nama lengkap sebelum admin mengonfirmasi. Jika satu kasus memiliki beberapa reviewer yang perlu diganti, tampilkan nama lengkap mereka langsung pada tombol agar admin bisa memilih orang yang tepat.

  1. Duplicate Aileen’s 1,440 × 900 “Baseline / pemantauan” frame beside “Alternatif (Tabel ringkas)”. Keep the 72 px header, 248 px sidebar, 40 px desktop content insets, Source Serif 4 headings, Hanken Grotesk UI, Cousine IDs, and existing badge and button tokens. Use auto-layout rows that grow with text. The export’s 315 px table sits inside a 303 px container.
  2. Use the same case on both sides. Annotate the named action with H6, row density with H7, and the neutral action treatment with H8. Give each replaceable reviewer their own named action when a case has two. Put the case code and round on a muted line above the full, regular-weight title in both steps (H6). Under “Konfirmasi penggantian reviewer”, place the outgoing and incoming reviewers side by side when space permits. Give the submitted reason its own line before the consequence (H5). Include a second slot, an unknown reviewer name, a row with no eligible replacement action, and a genuine empty candidate list.
  3. At 768 px, test the full title and action with the shared responsive shell. At 375 px, stack case, round, status and each reviewer’s reason/action. Preserve access to supported sorting and paging. Verify tab and dialog focus, Escape/cancel before submission, return focus, explicit field labels and readable badges. Any new shared-component variant goes through SCRUM-343.
  4. For data states use the shared components. Label loading “Memuat penugasan…”, empty “Tidak ada kasus yang perlu penugasan ulang”, and failure “Daftar penugasan gagal dimuat” with “Coba lagi”. For an ineligible list, explain that there are no eligible candidates. Show a fetch failure separately so admins can recover.
  5. PO and SA review the frame pairs, labels and role-specific rules before production coding. For SCRUM-360, ask a reviewer to locate the correct case version, request a revision and return to the queue. Ask an admin to replace the intended person in a two-slot round and explain the effect before confirming. Counterbalance which design admins see first. With comparable case lists, record time to locate the target, incorrect reviewer selections and whether admins can explain the consequence. Check the number of complete rows in the same viewport before comparing task results. Revise the designs and code from PO-agreed findings.
